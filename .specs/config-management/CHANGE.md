## Why（为什么做）

当前系统中所有可调参数（融合阈值、衰减因子、剪枝阈值、LLM 提示词模板、模型名称/温度/max-tokens 等）均硬编码在 `application-*.yml` 或 `classpath:/prompts/*.md` 文件中。管理员想调整任何一个参数（例如把融合阈值从 0.85 调到 0.80、更换 LLM 模型、优化提示词文案）都必须：

1. 修改源码文件
2. 重新构建 & 重启服务

这不仅操作成本高，还要求操作者具备开发背景。系统需要一个运行时配置管理能力，让 ADMIN 角色通过管理后台直接修改配置并手动触发重载生效。

## What（做什么）

新增**配置管理模块**，覆盖以下三类可动态管理的配置项：

| 类别 | 示例 | 存储方式 |
|------|------|---------|
| 业务参数 | `fusion.kp-matching.threshold`、`fusion.strategy.time-decay.factor`、`query.pruning.weak-threshold`、`query.token-budget.max-input-tokens` 等 | 数据库（键值对） |
| LLM 提示词 | `prompts/*.md` 中各模板文件的完整文本内容（system prompt + user prompt + few-shot） | 数据库（文本字段） |
| LLM 模型参数 | `spring.ai.openai.chat.options.model`、`temperature`、`max-tokens`、`base-url` 等 | 数据库（键值对） |

核心机制：
- 配置值持久化到 MySQL，系统启动时从 DB 加载并覆盖 yml 默认值
- 配置加载器抽象：各 `@ConfigurationProperties` 类改为从 DB 读取（保留 yml 默认值作为 fallback）
- Prompt 模板从 DB 加载，替换 `classpath` 文件读取
- 管理员通过前端页面修改 → 点击「应用配置」→ 后端重载缓存，业务逻辑即时使用新值（无需重启）

## 范围排除（这次不做）

1. **基础设施连接参数**：DB/Redis/Neo4j/MinIO 的连接地址/端口/密码等不在管理范围内（这些必须在容器启动前确定，运行时修改会导致连接断开）
2. **密码类配置加密存储**：v1 不引入配置值加密，敏感配置（如 API Key）通过 yml 环境变量注入，不纳入配置管理模块
3. **配置版本历史与变更审计**：v1 不记录谁在什么时候改了什么（Q3 选 B 而非 C）
4. **多环境配置同步**：dev/prod 环境各自独立管理，不提供跨环境配置复制/同步功能
5. **配置导入/导出**：不提供 JSON/YAML 格式的批量导入导出
6. **配置校验规则引擎**：v1 仅做基本类型校验（数字范围/非空），不引入可编程的校验规则

## 验收线（粗粒度，不是 AC）

- ADMIN 用户可在管理后台「系统配置」页面查看、修改、应用业务参数/提示词/模型配置
- 点击「应用配置」后，新的配置值对后续业务请求即时生效，无需重启服务
- 服务重启后，配置自动从数据库恢复，不丢失上次修改

## 风险与未知

- **配置加载顺序**：Spring Boot 的配置加载链路（`Environment` → `@ConfigurationProperties` → `@Value`）介入点需在 DESIGN 阶段仔细选型，避免破坏 Spring 既有配置优先级
- **提示词热更新与 LLM 调用并发**：提示词文本在 LLM 调用中途被修改的并发一致性问题，需在 DESIGN 阶段确定策略（快照读 vs 读写锁）
- **配置回滚**：v1 不提供版本历史，若管理员误改参数后「应用」，只能手动改回原值再次应用。风险可接受（操作频率低 + ADMIN 角色可控）
- **配置膨胀**：当前约 30+ 个可配置项，若未来快速增长，DB 键值对模型的查询效率需关注。v1 通过全量加载 + 内存缓存解决
