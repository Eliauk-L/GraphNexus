# REQUIREMENT: 文件处理状态流前端实时展示

- **Change ID**: `frontend-status-flow`
- **关联**: `@.specs/frontend-status-flow/CHANGE.md`、`@.specs/CONTEXT.md`

---

## 用户故事

- **US-1**：作为管理员，我想在文件列表中**实时看到文件处理的完整进度**（解析 → 抽取 → 融合 → 完成），以便判断图谱构建是否完成、何时可以查看子图。
- **US-2**：作为管理员，我想在状态展示中**一眼看清处理管线走到了哪一步**，以便快速了解还有哪些阶段未完成。
- **US-3**：作为管理员，我想在图谱可视化页选择文档时**看到该文档的处理状态**，以便避免在文档尚未完成图谱构建时尝试加载子图。

## 验收准则（AC）

### AC-1 · 轮询追踪完整处理管线

- **Given** 用户刚上传了一个文件并自动触发了解析（或手动点击了解析按钮）
- **When** 后端依次经历 PARSING → PARSED → EXTRACTING → EXTRACTED → FUSING → COMPLETED
- **Then** 文件列表中的状态列在 **每个阶段都能实时更新**（2 秒轮询间隔内），用户看到的状态依次为：解析中 → 已解析 → 抽取中 → 已抽取 → 融合中 → 已完成，不再卡在「已解析」
- **验证方式**: 上传一个 PDF 文件，观察文件列表状态列在 2 分钟内是否依次经历全部 6 个状态

### AC-2 · 轮询仅追踪活跃处理态，避免空转

- **Given** 文件列表中存在状态为 `UPLOADED`（等用户点解析）、`PARSED`（等异步抽取启动）、`EXTRACTED`（等融合）、`COMPLETED`（已完成）或 `FAILED`（失败）的文件
- **When** 页面上没有文件处于 `PARSING`、`EXTRACTING` 或 `FUSING` 状态
- **Then** 轮询自动停止，不再发送列表请求；页面不显示「实时刷新处理状态…」提示
- **验证方式**: ① 上传文件后不点解析，确认 10 秒内轮询停止；② 等文件走到 COMPLETED 后，确认轮询停止

### AC-3 · 最大轮询时长兜底

- **Given** 轮询已启动且持续运行
- **When** 轮询持续时间超过 5 分钟（300 秒）
- **Then** 轮询强制停止，即使仍有文件处于活跃处理态；状态列保留最后一次拉取的结果
- **验证方式**: 将最大轮询时长临时改为 10 秒，启动轮询后等待 10 秒确认停止（单元测试覆盖）

### AC-4 · 轮询仅在上传/手动解析后启动

- **Given** 用户通过路由导航进入文件管理页（非上传或手动解析操作后）
- **When** 页面挂载完成
- **Then** 轮询不自动启动（不调用 `startPolling()`）；页面加载一次列表数据后不再持续拉取
- **验证方式**: 从其他页面切换到文件管理页，打开浏览器 Network 面板，确认只有一次 `/api/v1/file/textbooks` 请求

### AC-5 · 管线进度可视化

- **Given** 文件列表中存在状态各异的文件（如一个 PARSING、一个 EXTRACTING、一个 COMPLETED）
- **When** 用户查看文件列表
- **Then** 状态列不再仅显示文字徽章，而是展示紧凑的**管线进度指示器**：清晰标示「解析 → 抽取 → 融合」三个阶段各自的完成/进行中/未开始状态；已完成阶段用成功色、进行中用动画色、未开始用中性色
- **验证方式**: 分别查看 PARSING、EXTRACTING、COMPLETED 三个文件的状态列，确认三者显示的进度条/步骤状态各不相同且正确

### AC-6 · 图谱页文档选择器展示处理状态

- **Given** 系统中存在已抽取/融合中/已完成的文档
- **When** 用户打开图谱可视化页，查看文档选择器下拉列表
- **Then** 每个文档选项旁显示其当前处理状态（文字 + 颜色标识）；处于 `EXTRACTING` 或 `FUSING` 的文档标记为「处理中」且置灰不可选；`COMPLETED` 的文档正常可选
- **验证方式**: 同时存在 EXTRACTING 和 COMPLETED 文档时，打开图谱页下拉框确认差异展示

### AC-7 · 子图加载后非终态提示

- **Given** 用户在图谱页选中文档加载了子图
- **When** 该文档当前状态为 `EXTRACTED`（融合未完成或融合失败回退），而非 `COMPLETED`
- **Then** 图谱画布上方显示一条信息提示条：「该文档图谱数据可能不完整 — 融合尚未完成」（不阻塞图谱浏览）
- **验证方式**: 手动选一个 EXTRACTED 状态文档加载子图，确认提示条出现；再选 COMPLETED 文档，确认提示条不出现

## 范围切分

### v1（本次必做）

- 修复 `INTERMEDIATE_STATES` 为仅含活跃态 `['PARSING', 'EXTRACTING', 'FUSING']`
- 最大轮询时长 5 分钟兜底
- 轮询仅在上传/手动解析触发后启动（移除页面挂载时的无条件 1 秒延迟启动）
- 管线进度指示器组件（替换/增强 StatusBadge）
- 图谱页文档选择器展示处理状态 + 非终态提示

### v2（下一轮考虑，不本次）

- WebSocket/SSE 服务端推送替代轮询，实现真正实时更新
- 按 `documentId` 单文件状态查询端点（替代全量列表轮询），降低带宽和后端压力
- 轮询自适应退避（文件状态持续不变时自动延长轮询间隔）
- 文件处理耗时统计（每个阶段耗时展示，帮助用户建立时间预期）
- 浏览器 Notification API 桌面通知（处理完成/失败时弹出）

### out（永远不做）

- 后端状态机变更（`FileStatus` 枚举、状态流转规则、Spring 事件机制均不在本次变更范围）
- 文件处理管线可暂停/可恢复/可取消
- 成绩文件的状态流展示（成绩无异步管线，上传即完成，不适用此机制）
- 移动端适配（V1 桌面端 ≥1280px，管线进度组件按桌面端设计）
- 暗黑模式（跟随全局 V1 决策不做 dark mode）

## 非功能性需求

- **性能**: 轮询每次拉取 `listFiles(1, 100)` 不超过 100 条记录，2 秒间隔 × 5 分钟 = 最多 150 次请求，后端可承受；管线进度组件渲染不触发额外网络请求
- **可访问性**: 管线进度指示器不使用纯颜色区分状态（搭配图标/文字），确保色弱用户可辨识
- **安全**: 无新增安全面（纯前端展示层变更，不引入新的数据输入或存储）
- **兼容性**: 与现有 Chrome/Firefox/Edge 120+ 兼容（`setInterval` 和 CSS 动画均为标准特性）
- **可观测性**: 前端 console 在 dev 模式下记录轮询启动/停止事件及原因（状态变化触发 / 超时触发 / 组件卸载触发），便于调试

## 依赖与假设

- 依赖现有 `GET /api/v1/file/textbooks` 列表端点（含 `status` 字段），行为不变
- 依赖现有 `GET /api/v1/file/textbooks/{id}` 单文件端点，用于精准状态查询（如需）
- 假设后端 `TextbookParsedEventListener`（`@Async`）在 PARSED 落库后 **通常 < 1 秒** 内启动抽取，PARSED→EXTRACTING 过渡间隙足够短，2 秒轮询间隔可覆盖
- 假设 LLM 抽取 + 融合总耗时 **通常 < 3 分钟**，5 分钟最大轮询留有 2 分钟裕量
- 假设文件列表总量在 V1 期间 **< 100 条**（管理后台场景），`listFiles(1, 100)` 一次拉全量足够
