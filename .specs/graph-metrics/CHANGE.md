## Why（为什么做）

宽图谱构建完成后（文档抽取 + CSV 成绩导入 + 融合），目前缺少对图结构本身的定量分析能力。具体场景：

- **教师视角**：想知道哪些知识点是"核心枢纽"——被大量前置依赖引用、被大量文档实体对齐到的 KP，这些是教学重点
- **学生诊断**：在智能问答剪枝时，如果能结合节点的中心性指标，可以在 Token 预算有限时优先保留"更重要"的节点，提升诊断质量
- **图谱质量评估**：度中心性异常高/低的节点可能暗示抽取错误或融合过度/不足，帮助发现数据质量问题

目前系统没有任何图算法能力，每次分析都需要人工遍历或凭经验判断。

## What（做什么）

在 Neo4j 宽图谱上引入 **Neo4j GDS（Graph Data Science）插件**，通过 Cypher 调用 GDS 过程，实现 PageRank 和度中心性（Degree Centrality）两种图指标的**可配置计算**，并通过 REST API 返回计算结果。**不持久化**到 Neo4j 节点属性。图谱数据变更后**自动触发重算**。

核心能力：
- 可配置投影范围（按节点类型 + 边类型过滤，默认全图）
- 支持 PageRank 和度中心性两种指标
- REST API 查询（不写入节点属性）
- 图数据变更后自动重算（事件驱动）

## 范围排除（这次不做）

- **不持久化**指标数值到 Neo4j 节点属性（v1 仅 API 返回，避免写放大）
- **不做**介数中心性、紧密中心性、特征向量中心性等 PageRank/度中心性以外的指标
- **不做**指标的历史版本比较（如"本次 PageRank vs 上次"的差异分析）
- **不做**基于指标的自动预警或异常检测
- **不做**前端图可视化（指标结果仅在 API JSON 中返回，可视化由前端自行决定）
- **不做**指标在智能问答剪枝中的自动集成（如按 PageRank 调整 Token 优先级），这留到后续 change

## 验收线（粗粒度，不是 AC）

1. 用户调用 `GET /api/v1/graph/metrics/pagerank?nodeTypes=KnowledgePoint&edgeTypes=PREREQUISITE_OF` 能拿到指定子图的 PageRank 值列表（JSON），延迟 2 秒内
2. 用户调用 `GET /api/v1/graph/metrics/degree` 能拿到度中心性（in/out/total），同样支持节点/边类型过滤
3. 用户导入一份新 CSV 成绩文件后，再次查询 PageRank 结果已自动更新（无需手动触发）

## 风险与未知

- **GDS 插件依赖**：Neo4j 5.x 容器需安装 GDS 5.x 插件。需确认 podman-compose 中 Neo4j 镜像是否已包含 GDS，或需切换至含 GDS 的镜像/自定义 Dockerfile
- **性能风险**：全图 PageRank 对大图可能是重操作。全图投影时需评估当前数据规模下的计算耗时，必要时加超时和降级策略
- **自动触发频率**：若短时间内多次文档抽取/CSV 导入/融合，可能触发频繁重算。需考虑去抖（debounce）或合并机制
- **GDS 内存消耗**：图投影到 GDS 内存图时，可能因数据规模过大导致 Neo4j 内存不足，需评估内存配置
- **图投影模型设计**：不同边类型的图投影方向性（有向/无向）影响 PageRank 语义。如 PREREQUISITE_OF 是明确有向边，但 ALIGNED_TO 方向性较弱。需在设计中明确哪些边参与投影及方向处理
