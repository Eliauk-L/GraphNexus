## Why（为什么做）

当前系统已实现主要业务功能（文档解析/图谱构建/融合/智能问答/成绩管理）和运维管理（系统健康/日志查看），但缺少运营层面的数据可视化管理。ADMIN 和 OPS_MANAGER 无法回答以下问题：

- 系统最近被用了多少？（谁在用、用得多频繁、哪个功能最常用）
- 文档处理效率如何？（上传了多少文档、解析完成率、处理耗时分布）
- 知识图谱长什么样？（各类型节点/边各有多少、按学科怎么分布、增长趋势如何）

这些信息对运营决策（资源调配、功能优化优先级、向管理层汇报）至关重要。

## What（做什么）

新增「运营管理」模块，包含三大统计维度：

1. **系统使用量统计**：用户活跃度（登录次数、活跃用户数、操作频次，基于新增的操作审计日志表）+ API 调用量（智能问答次数、文档上传/解析次数、各端点请求量）
2. **文档处理量统计**：文档总量、按状态分布、按学科分布、处理耗时统计、上传趋势（天/周/月）
3. **图谱节点/边分布**：按节点类型（Entity/KP/Category/Subject/Student/Exam）和边类型（ALIGNED_TO/PREREQUISITE_OF/TESTED/MASTERS 等）的计数分布 + 按学科维度的节点/边分布

展示形式：数字统计卡片 + 图表可视化（折线趋势图、柱状对比图、饼图分布图）。数据来源：实时查询现网（面板） + 定时快照落库（历史趋势）。

## 范围排除（这次不做）

- 操作审计日志的**完整实现**（本次仅记录统计所需的登录事件和关键操作，不做细粒度的字段变更审计、不做操作回放）
- **报表导出**功能（PDF/Excel 导出留到后续 change）
- **告警/通知**功能（如"文档处理失败率超过 X% 发告警"，留到后续 change）
- **多租户/学校级**隔离统计（v1 默认全系统统计，不做按学校/机构维度拆分）
- **实时 WebSocket 推送**（统计数据刷新走前端定时轮询，不引入 WebSocket）
- 图谱分布的**节点级详情钻取**（如点击"KnowledgePoint 500 个"跳转到列表——本次仅展示聚合数字和趋势，不做逐项列表页）

## 验收线（粗粒度，不是 AC）

- ADMIN 和 OPS_MANAGER 登录后可在左侧导航看到「运营管理」入口，点击进入运营仪表盘页面
- 页面展示三大区域（系统使用量、文档处理量、图谱分布），每区域含数字卡片 + 图表，数据真实可溯源
- 历史趋势可按天/周/月切换查看，数据来源于定时快照表
- 页面加载时间 ≤ 3 秒（含所有实时统计查询和图表渲染）

## 风险与未知

- **操作审计日志的写入性能影响**：每次登录/关键操作需额外写 `audit_log` 表，需评估对现有请求响应时间的影响。预期异步写入（`@Async` + 独立短事务）可消除阻塞
- **图谱分布实时查询的 Neo4j 开销**：按类型统计节点/边数需要全图 COUNT 查询，大图（>10 万节点）可能较慢。需评估是否走 GDS 或 Neo4j 内置统计过程，而不是裸 Cypher COUNT
- **定时快照任务调度方案**：项目当前未使用定时任务框架（无 `@Scheduled` / Quartz / XXL-JOB），需 DESIGN 阶段选型
- **图表库前-后端数据协议**：前端图表组件需要后端返回什么格式的统计数据（按天的时间序列？聚合数值？），需在 DESIGN/REQUIREMENT 阶段明确契约，避免前端开发时反复调整接口
