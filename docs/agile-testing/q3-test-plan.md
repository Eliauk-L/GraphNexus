## 一、Q3 象限定位

```
        面向业务（Business Facing）
                │
    Q2 ┌────────┼────────┐ Q3
       │  自动化  │ ★Q3★  │
       │  BDD   │  探索性  │
       │  场景   │  用户验收 │
  支撑  │  验收   │  可用性  │ 评判
  团队  ├────────┼────────┤ 产品
       │  自动化  │  自动化  │
       │  单元   │  性能   │
       │  接口   │  安全   │
    Q1 └────────┼────────┘ Q4
                │
        面向技术（Technology Facing）
```

| 维度 | Q3 说明 |
|------|--------|
| **核心问题** | "用户体验好吗？"、"有我们没想到的缺陷吗？"、"真的满足业务需求吗？" |
| **执行方式** | **以人工为主导**的探索性测试 + 用户验收测试 + 可用性评估 |
| **目标** | 发现自动化测试覆盖不到的缺陷，验证产品在实际使用中的体验和质量 |
| **关键特征** | 依靠人的直觉、经验和领域知识，发现意外行为和设计缺陷 |
| **为什么不可替代** | 探索性测试发现的缺陷约占线上问题的 **30-40%**，是自动化无法覆盖的最后防线 |

## 三、探索性测试（Exploratory Testing）

### 3.1 基于会话的测试管理（SBTM）

> 采用 Session-Based Test Management 方法组织探索性测试活动。

#### 会话定义模板

```
┌─────────────────────────────────────────────┐
│  Session Charter                             │
│  ─────────────                               │
│  Charter ID:   CH-{角色}-{序号}              │
│  测试角色:     管理员 / 教师 / 学生 / 运维    │
│  探索区域:     功能域 + 关注点                │
│  时间盒:       60 / 90 / 120 分钟            │
│  测试目标:     具体要探索什么                │
│  测试思路:     从哪些角度探索                │
│  交付物:       Session Report               │
└─────────────────────────────────────────────┘
```

#### 会话报告模板

```
┌─────────────────────────────────────────────┐
│  Session Report — CH-XX-XX                   │
│  ─────────────────────────                   │
│  执行人:     ____________                    │
│  执行时间:   ____________                    │
│  实际用时:   ____ 分钟                        │
│                                              │
│  # 测试覆盖了哪些区域 (Coverage)              │
│    · 功能A的路径1/2/3                        │
│    · 功能B的边界条件                          │
│                                              │
│  # 发现了什么 (Findings)                      │
│    BUG-001: [严重程度] 描述                   │
│    OBS-001: [观察] 描述                       │
│    QST-001: [疑问] 描述                       │
│                                              │
│  # 时间分配                                   │
│    测试执行: __%   缺陷记录: __%   环境准备: __%│
│                                              │
│  # 下一步建议                                 │
│    · 需要深入探索的方向                        │
│    · 需要修复的阻塞缺陷                        │
└─────────────────────────────────────────────┘
```

### 3.2 探索性测试 Charter 清单

#### 3.2.1 管理员视角

| Charter ID | 探索区域 | 时间盒 | 探索目标 | 关键探索思路 |
|-----------|---------|--------|---------|------------|
| **CH-ADM-001** | PDF 上传全流程 | 90min | 发现上传与处理过程中的意外行为 | 尝试各种"坏"PDF——空白页、混合方向、含大量公式、含图片表格、非标准编码中文、从 Word 直接另存为 PDF |
| **CH-ADM-002** | CSV 导入的鲁棒性 | 90min | 发现数据校验的遗漏和边界问题 | 尝试各种"脏"CSV——BOM头、换行符在字段中、超大文件、空文件、仅有表头无数据、混合编码、分隔符变化 |
| **CH-ADM-003** | 实体对齐审核体验 | 60min | 评估审核流程的效率和易出错点 | 模拟审核大量候选对（50+）时的操作疲劳、批量操作的反悔机制、误操作恢复 |
| **CH-ADM-004** | 知识体系编辑 | 60min | 发现树形结构操作的异常 | 快速增删改、拖拽跨越层级、同时打开多个编辑窗口、网络中断时的数据保存 |
| **CH-ADM-005** | 策略配置一致性 | 60min | 验证配置变更的实际生效路径 | 改策略前查询 → 改策略 → 再查询对比；修改后不保存直接离开 → 确认未生效 |
| **CH-ADM-006** | 管理员首页/导航 | 45min | 评估信息架构和操作效率 | 完成高频任务需要多少点击、菜单是否直观、重要信息是否在一屏内可见 |

#### 3.2.2 教师视角

| Charter ID | 探索区域 | 时间盒 | 探索目标 | 关键探索思路 |
|-----------|---------|--------|---------|------------|
| **CH-TCH-001** | 归因查询交互 | 90min | 发现查询输入和理解归因报告时的困惑点 | 尝试各种自然语言表述（口语化、专业术语、中英混用）；评估归因报告的可读性——新教师能否理解 |
| **CH-TCH-002** | 归因报告下钻 | 60min | 验证交互式追问的深度和准确性 | 连续下钻 3-5 层，检查每一层的因果逻辑是否合理；深度追溯是否出现循环论证 |
| **CH-TCH-003** | 班级薄弱概览 | 90min | 验证数据聚合的正确性和实用性 | 拿真实班级数据手工计算薄弱排名 → 与系统对比；切换不同班级/年级范围查看数据变化 |
| **CH-TCH-004** | 学生图谱可视化 | 60min | 评估可视化交互的流畅性和信息密度 | 图谱节点 100+ 时的渲染性能、缩放拖拽流畅度、颜色标注是否直观 |
| **CH-TCH-005** | 跨学科关联分析 | 60min | 验证跨学科路径发现的合理性 | 构造已知跨学科关联的场景（数学差→物理差），检查系统能否发现并正确归因 |
| **CH-TCH-006** | 报告导出与分享 | 45min | 发现导出格式和分享权限的问题 | 导出 PDF 的排版、HTML 的交互性、分享链接的权限验证、过期链接行为 |

#### 3.2.3 学生视角

| Charter ID | 探索区域 | 时间盒 | 探索目标 | 关键探索思路 |
|-----------|---------|--------|---------|------------|
| **CH-STU-001** | 学习概览理解度 | 60min | 评估学生对自己学习状态的认知准确度 | 让真实学生（或模拟学生视角）查看雷达图和薄弱列表，询问"你觉得这些信息准确吗？有用吗？" |

## 四、用户验收测试（UAT）

### 4.1 UAT 执行框架

```
┌─────────────────────────────────────────────────────┐
│                  UAT 四阶段流程                       │
│                                                      │
│  Phase 1          Phase 2          Phase 3          Phase 4
│  验收准备          验收执行          问题处置          验收签字
│  ────────         ────────         ────────         ────────
│  · 准备数据       · 执行用例       · 分级处理        · 各方签字
│  · 培训用户       · 记录结果       · 修复验证        · 上线决策
│  · 分配任务       · 收集反馈       · 回归确认        · 遗留问题
│                                                      │
│  ───────────────────────────────────────────────────  │
│  时间: 1-2天      时间: 3-5天      时间: 2-3天       时间: 1天
└─────────────────────────────────────────────────────┘
```

### 4.2 按角色的 UAT 任务

#### 4.2.1 管理员 UAT 任务

| UAT ID | 验收任务 | 业务场景 | 通过标准 | 优先级 |
|--------|---------|---------|---------|--------|
| **UAT-ADM-01** | 完整的数据入库流程 | 开学前，管理员需要将新学期的教辅 PDF（3-5份）和上学期期末考试成绩导入系统 | 3 份 PDF 全部成功解析并入库；CSV 成绩导入成功率 ≥ 95%；异常行有明确提示 | P0 |
| **UAT-ADM-02** | 实体对齐批量处理 | PDF 解析后系统生成了 30+ 条候选匹配对，管理员需要在一个工作日内完成审核 | 高置信度对可批量确认；中置信度逐一审核流程顺畅；整体耗时 < 30 分钟 | P0 |
| **UAT-ADM-03** | 知识体系搭建 | 管理员为"数学"学科建立两级分类结构，定义 5 条核心前置依赖 | 分类树操作直观；前置依赖关系创建后可在图谱中验证 | P0 |
| **UAT-ADM-04** | 策略配置与调优 | 管理员根据首次归因分析结果，调整剪枝策略参数以获得更好的分析效果 | 策略修改后立即在下一次归因查询中生效；可对比修改前后的分析结果差异 | P1 |

#### 4.2.2 教师 UAT 任务

| UAT ID | 验收任务 | 业务场景 | 通过标准 | 优先级 |
|--------|---------|---------|---------|--------|
| **UAT-TCH-01** | 日常归因分析 | 教师发现张三连续多次在二次函数题目上出错，使用系统查询根因 | 可自然语言输入查询；归因报告包含 ≥ 2 项根因及证据链；报告在 30 秒内返回 | P0 |
| **UAT-TCH-02** | 班级薄弱全景 | 期中考试后，教师查看全班薄弱知识点，为下一阶段教学调整提供依据 | Top-N 薄弱列表与教师经验判断一致（≥70% 吻合）；可下钻到具体学生 | P0 |
| **UAT-TCH-03** | 归因报告分享 | 家长会前，教师为张三生成家长版归因报告并分享链接 | PDF 排版规范可读；分享链接设置 7 天有效期后可正常访问 | P1 |
| **UAT-TCH-04** | 图谱可视化探索 | 教研讨论中，教师展示某学生的知识图谱给同事看 | 图谱渲染清晰（50+节点仍可辨识）；颜色标注（红/黄/绿）直观；交互流畅 | P1 |

## 五、可用性评估（Usability Evaluation）

### 5.1 Nielsen 十大启发式评估

> 由 2-3 名评估者独立对系统进行启发式评估，汇总发现的问题。

| # | 启发式原则 | GraphNexus 关注点 | 检查项 |
|---|-----------|-----------------|--------|
| **H1** | 系统状态可见性 | 异步处理（PDF 解析、LLM 分析）是否让用户感知到进度 | PDF 上传后是否有进度提示？归因查询等待时是否有 loading 状态？超时是否有预估剩余时间？ |
| **H2** | 系统与现实世界匹配 | 教育领域术语是否自然 | "归因分析""前置依赖""掌握权重"等术语对教师是否直观？是否需要额外解释？ |
| **H3** | 用户控制与自由 | 误操作是否有"紧急出口" | 实体合并后能否撤销？CSV 导入失败能否部分回滚？策略修改能否恢复？ |
| **H4** | 一致性与标准 | 各端交互是否统一 | 管理员/教师/学生端的导航结构、按钮样式、提示文案是否一致？ |
| **H5** | 错误预防 | 关键操作是否有确认 | 批量合并实体前是否展示影响面？删除知识点是否检查关联关系？ |
| **H6** | 识别而非回忆 | 信息是否可见而非需记忆 | 归因查询时学生姓名和知识点是否支持搜索/自动补全？而非要求教师记忆学号？ |
| **H7** | 灵活性与效率 | 高级用户是否有快捷操作 | 管理员是否支持批量操作？教师是否支持快捷键/常用查询模板？ |
| **H8** | 美观与简约 | 信息密度是否合理 | 归因报告是否重点突出？图谱可视化是否过于密集？运营看板是否一屏能理解？ |
| **H9** | 帮助用户识别和恢复错误 | 错误信息是否可操作 | 上传失败后是否提示具体原因和解决建议？LLM 返回格式错误时是否给用户可理解的提示？ |
| **H10** | 帮助与文档 | 是否需要额外帮助 | 首次使用的教师能否在没有培训的情况下完成归因查询？ |

### 5.2 角色特定可用性关注点

#### 管理员可用性

| 场景 | 可用性目标 | 评估方法 |
|------|-----------|---------|
| 首次配置系统 | 30 分钟内完成基础配置（学科创建 + 策略配置 + 知识体系搭建） | 计时 + 任务完成率 |
| 批量审核实体对齐 | 50 条候选对在 20 分钟内审核完成，误操作率 < 5% | 计时 + 错误计数 |
| PDF 上传反馈 | 上传后立即看到状态，无需刷新页面 | 观察 + 访谈 |
| CSV 导入错误修正 | 错误提示能直接定位到 CSV 具体行，无需下载文件自查 | 任务完成率 |

#### 教师可用性

| 场景 | 可用性目标 | 评估方法 |
|------|-----------|---------|
| 首次归因查询 | 未经培训的教师能在 2 分钟内完成第一次查询并理解报告 | 计时 + 理解度测试 |
| 归因报告理解度 | 报告中 ≥ 80% 的信息能被教师正确解读 | 理解度问卷 |
| 班级薄弱概览 | 一眼（5 秒内）能识别出 Top 3 薄弱知识点 | 眼动追踪 / 观察 |
| 追问下钻 | 点击下钻后新报告 < 10 秒返回，因果链清晰 | 计时 + 访谈 |

#### 学生可用性

| 场景 | 可用性目标 | 评估方法 |
|------|-----------|---------|
| 学习概览理解 | 学生能独立看懂雷达图（颜色、位置含义）无需解释 | 理解度测试 |
| 复习路径行动 | 学生看完复习路径后知道"接下来该做什么" | 任务完成率 |
| 移动端适配 | 学生端在手机浏览器上可正常使用 | 响应式测试 |

## 六、LLM 输出质量评审

> GraphNexus 的独特之处在于核心价值交付依赖 LLM 输出质量。Q3 必须包含对 LLM 生成内容的人工质量评审。

### 6.1 归因报告质量评审维度

| 维度 | 评分标准 (1-5) | 权重 | 评审方法 |
|------|---------------|------|---------|
| **准确性** | 归因结论是否与被分析学生的实际学习数据吻合 | 30% | 评审者事先了解学生的真实学习情况，对照报告判断 |
| **完整性** | 是否覆盖了所有显著薄弱点及相关前置依赖链 | 20% | 检查是否遗漏了已知的薄弱知识点 |
| **证据充分性** | 每条根因是否有充分的证据链支撑（权重+得分+时间趋势） | 20% | 逐条检查证据链的数据引用是否准确 |
| **可操作性** | 教师能否根据报告结论直接制定辅导计划 | 15% | 教师评审者判断"看完后我知道该怎么做吗" |
| **可读性** | 报告结构和语言是否清晰易懂 | 10% | 非技术背景教师能否独立阅读理解 |
| **无幻觉** | 报告中是否存在编造的数据或不存在的事件引用 | 5% | 与数据库原始数据逐一比对 |

### 6.3 教学建议质量评审

| 维度 | 评估方法 |
|------|---------|
| **教育合理性** | 由学科教研组长审阅"补救路径"是否遵循正确的学习顺序 |
| **资源匹配度** | 检验推荐的教辅页码/题号是否真实存在并确实相关 |
| **难度递增** | 建议的练习序列是否呈合理的难度递增 |
| **时间估算准确** | 建议的学习时间与实际教学经验是否相符 |

### 6.4 Prompt 敏感性探测

> LLM 对输入变化可能过度敏感，需要进行人工探测。

| 探测方向 | 测试方法 | 关注点 |
|---------|---------|--------|
| **同义表述** | 用 3 种不同表述描述同一个归因查询场景，对比 LLM 输出 | 报告结构和结论是否一致 |
| **对抗输入** | 输入含误导性描述的查询——"张三 数学很好 为什么二次函数差" | LLM 是否被前半句误导 |
| **生僻知识点** | 查询系统中学过但仅有一次事件记录的冷门知识点 | 数据稀疏时 LLM 是否诚实告知"数据不足"而非编造 |
| **多学生混淆** | 输入"张三和李四 谁数学更好"（非归因查询） | 系统是否正确拒绝或路由到合适的分析类型 |

## 七、缺陷严重程度分级

> Q3 发现的缺陷需要分级处理，决定是否阻塞上线。

| 级别 | 定义 | GraphNexus 示例 | 处理策略 |
|------|------|----------------|---------|
| **P0 · 阻断** | 核心功能不可用，无变通方案 | 归因查询始终返回 500 错误；实体合并导致数据丢失 | 修复后必须重新验收 |
| **P1 · 严重** | 核心功能严重受损，有变通方案但不可接受 | PDF 处理成功率 < 80%；归因报告频繁出现幻觉引用 | 必须修复，可并行验收其他功能 |
| **P2 · 一般** | 非核心功能缺陷，或核心功能有可接受的变通方案 | 学生端复习路径排序偶尔不合理；图谱可视化颜色标注不够直观 | 排入下一迭代修复 |
| **P3 · 建议** | 体验优化建议，不影响功能 | 按钮位置不够便捷；提示文案可以更友好 | 纳入产品 backlog |
