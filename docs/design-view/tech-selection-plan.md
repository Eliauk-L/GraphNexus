### 1.2 选型原则

| 原则 | 说明 |
|------|------|
| **框架负责通用的，自研负责差异化的** | 图谱构建用 LlamaIndex 现成管线；剪枝/权重/上下文构建自研 |
| **Python 全栈** | 数据科学 + LLM 生态 + Web 开发均统一为 Python，减少异构复杂度 |
| **异步优先** | FastAPI + Neo4j async driver + httpx，全链路 async/await |
| **Pydantic v2 驱动** | 所有接口数据传输用 Pydantic v2 建模，类型安全且高性能 |
| **MVP 先跑通核心链路** | PDF→图谱→事件→剪枝→上下文→LLM→归因报告，一条链路贯通 |

### 2.1 L1 · 表示层 — 前端技术栈

| 技术 | 版本 | 用途 | 选型理由 |
|------|------|------|---------|
| **React** | 18.x | UI 框架 | 生态最成熟，社区最大，Ant Design 原生支持 |
| **TypeScript** | 5.x | 类型系统 | 与后端 Pydantic v2 共同形成端到端类型安全 |

### 2.2 L2 · 应用层 — Web 框架

#### 2.2.1 核心选型：FastAPI

| 维度 | FastAPI | Flask | Django | Sanic |
|------|---------|-------|--------|-------|
| **异步原生** | ✅ async/await 一等公民 | ❌ 需扩展 | ⚠️ 部分支持 | ✅ |
| **Pydantic 集成** | ✅ 原生 v2 | ❌ 需插件 | ❌ 需 DRF | ❌ |
| **自动 OpenAPI** | ✅ 内置 Swagger | ❌ 需插件 | ⚠️ DRF-Spectacular | ⚠️ |
| **类型安全** | ✅ 编译时 + 运行时 | ❌ | ❌ | ❌ |
| **生态成熟度** | 极高 | 极高 | 极高 | 中 |
| **机器学习/LLM 兼容** | ✅ Starlette 生态 | ⚠️ | ⚠️ | ⚠️ |
| **学习成本** | 低 | 低 | 高 | 中 |

**选型结论：FastAPI**。理由：
1. 原生 async/await，与 Neo4j async driver、httpx 无缝配合
2. 原生 Pydantic v2 支持，领域层实体 → 接口 DTO 直接复用
3. 自动生成 Swagger UI，前后端联调零成本
4. GraphNexus 需要与 OpenAI/Anthropic SDK（均支持 async）配合，全链路异步可最大化吞吐

#### 2.2.2 辅助选型

| 技术 | 版本 | 用途 | 选型理由 |
|------|------|------|---------|
| **Uvicorn** | 0.34.x | ASGI 服务器 | `uvloop` + `httptools` 实现超高并发，生产级 HTTP 服务器 |
| **httpx** | 0.28.x | 异步 HTTP 客户端 | 替代 requests，支持 async，用于测试 FastAPI 端点和调用外部 API |

### 2.3 L3 · 领域层 — 图谱 & AI

#### 2.3.1 图谱存储：Neo4j

| 维度 | Neo4j | ArangoDB | JanusGraph | NebulaGraph | 自研 |
|------|-------|----------|------------|-------------|------|
| **图查询语言** | Cypher (最成熟) | AQL | Gremlin | nGQL | — |
| **Python 驱动** | ✅ `neo4j` 官方，async 原生支持 | ⚠️ | ⚠️ | ⚠️ | — |
| **LLM/KG 生态** | ✅ GraphRAG/LlamaIndex/LangChain 均原生支持 | ❌ | ❌ | ❌ | — |
| **图算法** | ✅ GDS 库 (PageRank, 社区检测) | ⚠️ | ⚠️ | ⚠️ | — |
| **部署运维** | 简单 | 中等 | 复杂 | 复杂 | — |
| **社区/文档** | 最成熟 | 中等 | 中等 | 小 | — |

**选型结论：Neo4j 5.x**。理由：
1. **Cypher 表达能力最强** — 剪枝引擎的 BFS 多跳遍历 (`MATCH (n)-[*1..N]-`) 在 Cypher 中是最自然的表达
2. **GDS 库开箱即用** — PageRank、社区检测等图算法直接调用，无需自研
3. **LlamaIndex 原生集成** — `llama-index-graph-stores-neo4j` 直接打通 PDF→Neo4j
4. **async driver** — `neo4j` Python driver 5.x 原生支持 `async/await`，与 FastAPI 全链路异步一致

```
PDF → [LlamaIndex] → Neo4j
CSV → [pandas解析] → Neo4j
剪枝 ← [Cypher BFS] ← Neo4j
权重 ← [Cypher SET] ← Neo4j
上下文 ← [子图序列化] ← Neo4j
```

#### 2.3.2 图谱构建框架：LlamaIndex

| 维度 | LlamaIndex PropertyGraphIndex | LangChain GraphCypherQAChain | 自研 NER/RE 管线 | Microsoft GraphRAG |
|------|------|------|------|------|
| **PDF→图谱 全链路** | ✅ 一条链路打通 | ⚠️ 需自行串联 | ❌ 工作量巨大 | ⚠️ 偏重社区摘要 |
| **Neo4j 集成** | ✅ 原生 `Neo4jPropertyGraphStore` | ⚠️ 需手写 Cypher | ⚠️ | ❌ |
| **实体抽取** | ✅ `LLMEntityExtractor` 开箱即用 | ⚠️ | ❌ | ✅ (但非结构化) |
| **代码侵入性** | 低 (封装在 ingestion 层) | 中 | — | 高 (框架侵入全链路) |
| **可替换性** | 高 (单一模块职责) | 中 | — | 低 |

**选型结论：LlamaIndex**。理由：
1. **一条链路打通 PDF→Neo4j**：`SimpleDirectoryReader` → `LLMEntityExtractor` → `Neo4jPropertyGraphStore`
2. **框架边界清晰**：仅用于 M3 入库引擎的 PDF 流水线，不侵入剪枝/权重/上下文
3. **可后续替换**：如果后期需要更精细的 NER/RE，可以替换 LLMEntityExtractor 为自研模型

**框架使用边界（关键设计决策）**：

```
LlamaIndex 负责 (不改)：
  ✅ SimpleDirectoryReader          — PDF 文件加载
  ✅ LLMEntityExtractor             — NER/RE 抽取（调用 LLM）
  ✅ Neo4jPropertyGraphStore        — Neo4j 连接与基础读写
  ✅ LLM 抽象层                      — 模型调用封装

自研负责 (不在框架内)：
  ❌ PruningEngine                  — 剪枝引擎（BFS Cypher）
  ❌ WeightEngine                   — 权重引擎（时间衰减 + 事件驱动）
  ❌ ContextBuilder                 — 上下文构建（子图→Prompt）
  ❌ EntityAligner                  — 实体对齐（模糊匹配 + 自融合并）
  ❌ AttributionQueryService        — 归因查询编排（全链路串联）
  ❌ PrerequisiteLoader             — 前置依赖加载（YAML→Neo4j）
```

#### 2.3.3 LLM 调用：OpenAI SDK + Anthropic SDK

| 维度 | OpenAI SDK | Anthropic SDK | LangChain LLM 抽象 | LiteLLM |
|------|-----------|--------------|-------------------|---------|
| **直接性** | ✅ 直连，零中间层 | ✅ 直连 | ⚠️ 多一层抽象 | ⚠️ 多一层代理 |
| **async 支持** | ✅ 原生 | ✅ 原生 | ✅ | ✅ |
| **模型切换灵活性** | ⚠️ 需自行封装 | ⚠️ | ✅ 配置即可 | ✅ 配置即可 |
| **可控性** | ✅ 完全控制重试/超时/降级 | ✅ 完全控制 | ⚠️ 受框架约束 | ⚠️ |
| **额外依赖** | 0 | 0 | +20+ 包 | +1 服务 |

**选型结论：直接使用 OpenAI SDK + Anthropic SDK**，通过自研 `LLMGateway` 封装。理由：
1. **零额外依赖** — 不需要 LangChain 那么大的一套生态
2. **完全控制** — 重试策略、超时、降级、配额管理全部自控
3. **网关模式** — `LLMGateway` 封装两个 SDK，外部只依赖 `ILLMGateway` 接口

### 2.4 L4 · 基础设施层 — 中间件 & 存储

| 技术 | 版本 | 用途 | 选型理由 |
|------|------|------|---------|
| **Neo4j** | 5.27.x | 图数据库 | 宽图谱存储，Cypher 查询，GDS 图算法（见 §2.3.1） |
| **PostgreSQL** | 16.x | 关系数据库 | 结构化数据存储：学生/教师/班级主数据、LLM 调用记录、系统日志、运营统计数据 |
| **Redis** | 7.x | 缓存 & 会话 | 热点子图缓存（同班学生共享剪枝结果）、会话管理、权重衰减定时任务分布式锁 |
| **MinIO / S3** | — | 文件存储 | PDF 教辅文件、CSV 导入文件、归因报告导出的对象存储 |
| **RabbitMQ** | 3.13.x | 消息队列 | PDF 解析异步任务、权重批处理、通知发送；解耦耗时操作，提升 HTTP 响应速度 |

#### 2.4.1 为什么需要 PostgreSQL（而非仅 Neo4j）？

Neo4j 擅长**图遍历**（剪枝、权重、前置依赖链），但不适合：
- 主数据的**分页列表查询**（学生列表、班级列表、教师列表 10w+ 行高效分页）
- **结构化日志存储**（LLM 调用日志的按时间/模型/成本多维聚合查询）
- **运营统计**（文档产能、数据时效等聚合计算）

因此采用 **Neo4j + PostgreSQL 双数据库** 的混合存储策略：

```
┌──────────────────────────────────────────────┐
│              混合存储架构                      │
│                                              │
│  Neo4j (图数据库)                              │
│  ├── 知识点节点 + 关系 (知识图谱)              │
│  ├── 学生掌握关系 (权重, 动态变化)             │
│  ├── 事件节点 (考试/作业/测验)                 │
│  ├── 文档-知识点抽取关系                       │
│  ├── 剪枝子图 (运行时生成)                     │
│  └── 前置依赖链                                │
│                                              │
│  PostgreSQL (关系数据库)                        │
│  ├── 学生主数据 (CRUD, 分页列表)               │
│  ├── 教师/班级主数据                           │
│  ├── 用户/权限/角色                            │
│  ├── LLM 调用日志 (成本分析)                   │
│  ├── 系统日志                                  │
│  ├── 运营统计看板数据                           │
│  └── 剪枝策略配置 (非图结构数据)                │
│                                              │
│  一致性策略:                                    │
│  ├── 学生学号: PG 为 source of truth          │
│  ├── 知识点 ID: PG 为 source of truth          │
│  ├── Neo4j 通过 ID 引用 PG 实体                │
│  └── 事件触发最终一致性校验                      │
└──────────────────────────────────────────────┘
```

#### 2.4.2 Redis 的定位

```
Redis 缓存策略
├── 热点子图缓存 (TTL: 5 min)
│   同一班级学生共享剪枝结果，避免重复 BFS
├── 会话管理 (TTL: 根据登录态)
│   分布式 Session，支持 K8s 多 Pod
├── 分布式锁 (TTL: 任务执行时长)
│   权重衰减定时任务防重执行
└── 速率限制 (TTL: 1 min 时间窗口)
    LLM API 调用配额滑动窗口计数器
```

#### 2.4.3 消息队列的定位

```
RabbitMQ 异步任务
├── PDF 解析任务
│   上传 PDF → 立即返回 (状态=待处理) → 后台 LlamaIndex 处理 → 完成通知
├── 权重批处理任务
│   CSV 导入成绩 → 触发权重调整事件 → 异步更新图谱 → 权重变更日志
├── 时间衰减定时任务
│   每日凌晨 Cron 触发 → MQ 分发 → 按班级/学科并行衰减计算
└── 通知发送
    分析完成/PDF处理完成 → 异步发送邮件/站内消息
```

## 五、选型决策树

```
GraphNexus 技术选型全景决策树
════════════════════════════════

存储层:
  ├── 图数据 (实体+关系+图遍历) → Neo4j ✅
  ├── 结构化数据 (主数据+日志+统计) → PostgreSQL ✅
  ├── 缓存/会话/分布式锁 → Redis ✅
  ├── 文件存储 (PDF/CSV/导出) → MinIO (S3) ✅
  └── 异步消息 → RabbitMQ ✅

计算层:
  ├── PDF→图谱 流水线 → LlamaIndex ✅ (框架，不改)
  ├── 剪枝引擎 (BFS子图) → 自研 Cypher ✅ (差异化核心)
  ├── 权重引擎 (衰减+事件) → 自研 Python ✅ (差异化核心)
  ├── 上下文构建 → 自研 Python ✅ (差异化核心)
  ├── 实体对齐 (模糊匹配) → thefuzz + 自研 ✅
  └── LLM 调用 → OpenAI/Anthropic SDK (直接) ✅

通信层:
  ├── HTTP API → FastAPI ✅
  ├── 异步任务 → RabbitMQ ✅
  └── 前端 ↔ 后端 → REST + Swagger ✅

类型系统:
  ├── 后端 → Pydantic v2 ✅ (运行时校验)
  ├── 前端 → TypeScript ✅ (编译时校验)
  └── 共享类型 → 手动同步 (MVP阶段)
```

## 六、与同类方案的对比

| 维度 | 本方案 | 全 LangChain 方案 | 全 LlamaIndex 方案 | Microsoft GraphRAG |
|------|--------|-------------------|--------------------|--------------------|
| **图谱构建** | LlamaIndex (仅 ingress) | LangChain GraphCypherQAChain | LlamaIndex 全链路 | 自研（社区摘要） |
| **图谱存储** | Neo4j | Neo4j | Neo4j | 文件/内存 |
| **剪枝引擎** | 自研 Cypher BFS ✅ | 框架受限 | 框架受限 | ❌ 无此概念 |
| **权重引擎** | 自研时间衰减 ✅ | ❌ 不支持 | ❌ 无此概念 | ❌ 无此概念 |
| **上下文构建** | 自研 tiktoken 预算 ✅ | 框架控制 | 框架控制 | 框架控制 |
| **LLM 调用** | 直连 SDK | 框架抽象 | 框架抽象 | 框架抽象 |
| **Web 框架** | FastAPI (异步) | 无内建 | 无内建 | 无内建 |
| **数据库混合** | Neo4j + PG + Redis | Neo4j only | Neo4j only | 无传统 DB |
| **依赖包数量** | ~15 | ~40+ | ~30+ | ~20+ |
| **差异化控制力** | 极高 ✅ | 低 | 低 | 低 |
| **20天交付可行性** | ✅ 高 | ⚠️ 中 | ⚠️ 中 | ❌ 低 |

**结论**：本方案是唯一同时满足以下四个约束的方案：
1. PDF→图谱 全链路（靠 LlamaIndex）
2. 剪枝 + 权重 + 上下文 自研差异化（不依赖框架）
3. Web 服务完整交付（FastAPI 生产级）
4. 20 天 MVP 可交付（最小依赖、最精准边界）

## 七、选型风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| **LlamaIndex NER/RE 质量不达标** | 图谱实体/关系质量差，归因分析不准 | 中 | 预留Prompt调优时间(Day 8-9)；备选：手动标注种子实体 |
| **Neo4j BFS 子图偏大** | Token 超预算，LLM 成本飙升 | 中 | 跳数=3 硬限制 + Top-K 邻居截断 + tiktoken 预算兜底 |
| **OpenAI API 不可用** | LLM 调用失败，核心链路中断 | 低 | LLMGateway 内置 Anthropic 降级；本地 Mock 模式开发 |
| **PostgreSQL + Neo4j 双写一致性问题** | 学生数据与图谱不一致 | 中 | 学号/知识点ID 以 PG 为 source of truth；事件驱动最终一致性校验 |
| **Pydantic v2 与 LlamaIndex 版本冲突** | 运行时错误 | 低 | 锁定版本号，CI 中加 `pip check` 自动检测依赖冲突 |
