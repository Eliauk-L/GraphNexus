### 1.2 参与者详表

| # | 参与者 | 英文标识 | 一句话定位 | 核心诉求 | 对应角色编号 |
|---|--------|---------|-----------|---------|------------|
| **A1** | 管理员 | Administrator | 数据资产的管理者 | 高效完成教辅资料与成绩数据的入库、实体对齐、知识体系构建与策略配置 | #47 |
| **A2** | 教师 | Teacher | 价值消费者与数据生产者 | 精准定位学生薄弱点，获取可行动的辅导建议；上传班级作业/测验数据 | #48 |
| **A3** | 学生 | Student | 数据的来源与受益者 | 了解自身学习状态与知识薄弱点，获取个性化复习路径 | #49 |
| **A4** | 运维人员 | OperationsStaff | 系统稳定性的保障者 | 保障服务高可用运行，管理日志、备份与定时任务 | #50 |
| **A5** | 运营人员 | OperationsManager | 系统效果的度量者 | 量化系统使用情况与业务价值 | #51 |
| **A6** | LLM 服务 | LLM Service | 外部 AI 能力提供者 | 接收结构化 Prompt，返回分析结果 | — |

> **说明**：A6（LLM 服务）是外部系统参与者，GraphNexus 通过 M5.LLMGateway 与之交互。其余 5 类参与者均为人类用户。

### 1.3 参与者关系

```
                        ┌──────────────┐
                        │   管理员(A1)  │
                        │ 数据资产管理  │
                        └──────┬───────┘
                               │ 泛化（管理员是超级角色，可执行教师的所有用例）
                               ▼
                        ┌──────────────┐
                        │   教师(A2)    │
                        │ 教学分析与    │
                        │ 数据生产      │
                        └──────────────┘
                               │
            ┌──────────────────┼──────────────────┐
            │                  │                  │
            ▼                  ▼                  ▼
     ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
     │  学生(A3)     │  │ 运维人员(A4)  │  │ 运营人员(A5)  │
     │ 学习状态感知  │  │ 系统稳定性    │  │ 效果度量      │
     └──────────────┘  └──────────────┘  └──────────────┘
```

- **管理员 → 教师（泛化）**：管理员拥有教师的全部权限，此外还拥有系统配置、数据管理等特权操作
- 学生、运维人员、运营人员为独立的参与者，各自拥有互不重叠的用例集合

## 四、用例关系说明

### 4.1 关系类型

| 关系类型 | UML 符号 | 语义 | 使用场景 |
|---------|---------|------|---------|
| **包含 (include)** | `<<include>>` | 基础用例**必然**调用被包含用例 | 复用共享行为，如多个用例都需要权限校验 |
| **扩展 (extend)** | `<<extend>>` | 基础用例在特定条件下**可选**调用扩展用例 | 可选功能增强，如归因查询可选扩展为教学建议 |
| **泛化 (Generalization)** | `──▷` | 子参与者继承父参与者的所有用例 | 管理员继承教师的全部用例 |

### UC-01 ★ 教辅 PDF 上传与图谱构建

| 维度 | 说明 |
|------|------|
| **用例编号** | UC-01 |
| **用例名称** | 教辅 PDF 上传与图谱构建 |
| **参与者** | 管理员 (A1) |
| **优先级** | P0 — 核心链路起点 |
| **前置条件** | 管理员已登录系统；学科分类已定义 |
| **后置条件（成功）** | PDF 解析完成，知识点和关系写入 Neo4j，处理结果反馈给管理员 |
| **后置条件（失败）** | 文档标记为 FAILED 状态，失败原因记录，管理员收到通知 |
| **触发事件** | 管理员上传一份教辅 PDF 文件 |
| **涉及模块** | M3（入库引擎）、M1（权限校验）、M2（知识点匹配）、M7（通知） |
| **MVP 范围** | ✅ 是（Story 1） |

**主成功流程**：

```
1.  管理员选择学科分类，上传 PDF 文件
2.  系统校验文件格式（PDF）和大小（<限制值）
3.  系统创建 Document 实体，状态 = UPLOADED
4.  系统异步启动处理流水线：
    4a. 版面分析 — 识别正文/标题/表格/公式区域
    4b. 实体抽取(NER) — 提取概念、公式、定理、定义

    4d. 图谱导入 — 创建实体节点和关系边，关联文档来源元数据
5.  系统更新 Document 状态 = COMPLETED
6.  系统生成处理摘要（抽取实体数、关系数、耗时、置信度分布）
7.  系统通过 M7 通知服务向管理员发送完成通知
```

## 附录 B：用例粒度说明

本文档的 29 个用例均定位为**用户目标级（User Goal Level）**——每个用例代表参与者与系统之间一次完整的、产生可观测业务价值的交互。用例的粒度遵循 Cockburn 用例层级中的"海平面"原则：

- **不太细**：不把"输入查询关键词""点击搜索按钮"列为独立用例
- **不太粗**：不把"使用系统所有功能"作为一个用例
- **判断标准**：一个用例完成后，参与者可以满意地离开，而不需要立即做下一个操作
