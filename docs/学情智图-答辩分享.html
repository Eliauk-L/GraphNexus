系统概述

学情智图 系统概述

BACKGROUND

教育场景下 AI 上下文的三大挑战

🏝️

数据源异构与信息孤岛

成绩表、教辅 PDF 分散在不同系统中，AI 难以获取全面立体的背景信息。成绩以 Excel/CSV 表格存储，知识点定义隐含在 PDF 段落中，两者从未被打通。

🔗

上下文关联弱

传统关键词检索无法揭示"考试成绩→知识点掌握→前置依赖→教辅原文"的深层关联。学生反复出错时，教师只能凭直觉判断根因，缺乏有证据链支撑的系统性诊断。

🔊

上下文噪音大

直接输入大量原始数据会导致LLM 上下文窗口溢出和"幻觉"，缺乏面向特定任务（如学生薄弱点诊断）的精准上下文生成机制。

学情智图是什么？

基于 知识图谱 + 大语言模型 的教育智能分析平台

将教辅文档和考试成绩转化为知识图谱

为教师提供从"知道学生错了"升级为"知道学生为什么错"的精准诊断能力

🔗

三条核心链路

📄 文档 + 成绩 → 独立图谱 教辅文档与考试成绩分别构建知识图谱
🔗 独立图谱 → 动态宽图谱 多源图谱自动融合去重，并实现权重动态更新
🧠 宽图谱 → 诊断 任务驱动子图剪枝+LLM分析，生成根因+证据链

学情智图 核心链路设计

PIPELINE 1

文件上传与知识图谱

文件处理：上传→MinIO存储+内容去重→返回存储路径→调用解析接口→策略模式选择解析器(PDF/TXT/CSV/Excel)→短事务状态管理
图谱构建：Prompt组装(占位符+动态填充节点/边类型+少样本)→LLM调用(3次重试+格式校验)→Neo4j原子写入+同名去重

关键决策

决策方案
文件存储与解耦MinIO 存储 + 内容去重，返回文件ID，上传与解析解耦
解析器策略策略模式实现多类型解析：PDF / TXT / CSV / Excel
状态管理手动短事务管理，避免长事务包裹导致前端无法及时感知处理状态
删除原子性短事务检查考试关联→设置删除中状态→事件通知图谱删除→最后删文件，保证各组件一致
成绩管理成绩不存储文件，直接落库为考试记录
Prompt 外置带占位符的 md 文件 + 节点/边类型枚举动态填充 + 按学科少样本（学科增多文件爆炸）
LLM 容错3 次重试 + JSON Schema 格式校验，失败时修改提示词要求严格输出合法格式
Neo4j 写入原子性操作 + 同名知识节点简单去重

PIPELINE 2

图谱融合与权重动态更新

融合发起 → 按学科分组KP → 并查集两两合并相似KP → 构造融合组 → 边重定向到主KP → 找出受影响学生 → 权重动态重算 → FusionLogDO 记录快照

关键决策

决策方案
实体对齐并查集思想两两合并相似知识点；相似度计算：精确匹配 / 字符 Jaccard
合并操作被融合KP的边重定向到主KP，Neo4j TransactionTemplate 原子操作
受影响学生通过学科和知识点关联找出受影响学生，精准更新而非全量重算
权重更新策略时间衰减策略weight = Σ(avgScoreRatei × factormonthsAgoi) / Σ(factormonthsAgoi)，avgScoreRatei 为知识点在某次考试中的平均得分（不同题目涉及相同知识点）；简单平均策略
日志记录fusion_log 实时记录完整快照（源→目标KP映射 + MASTERS变更前后值），为回滚保留扩展

PIPELINE 3

剪枝子图与学情诊断

用户查询 → LLM意图识别 → 按意图路由处理逻辑 → 实体提取(学生/班级+学科) → 图游走(薄弱KP+前置依赖链展开) → 子图拼接+截断 → 序列化上下文 → LLM生成HTML+SVG诊断报告 → 持久化存储+导出

关键决策

决策方案
意图识别LLM 灵活诊断，目前实现学生学科诊断 + 班级学科诊断两种意图
班级诊断查询班级学生列表 → 每学生掌握度查询 → 班级级知识点聚合 → 筛选薄弱KP
学生诊断从单个学生出发进行图游走：薄弱KP → 前置依赖链展开 → 子图构造
截断机制子图过大时按节点重要性评分截断：掌握度越低 + 度中心性越高 → 分数越高（越应保留）
输出格式HTML+SVG 结构化诊断报告，含根因链、数据图表、依赖图
诊断持久化诊断记录存入数据库，支持导出
导出修复AI 最初使用 StreamingResponseBody 异步流式导出 → 线程切换致 Spring Security 认证丢失 → 改为同步字节流传输

学情智图 总结与展望

SUMMARY

总结

前期系统设计的重要性

前期系统设计能够极大地明确开发方向，减少弯路和返工。即便真正开发过程中与前期设计存在不一致，这也是一个反复修改、持续琢磨的过程——设计不是一成不变的，而是在实践中不断迭代优化。好的前期设计为团队提供了统一的技术语言和决策依据。

Vibecoding 不是万能的

AI 生成的代码正确率很高，但在理解上下文、梳理调用链方面仍需要人去完成。以下是实际踩过的两个典型坑：

技术版本差异

AI 不了解项目实际运行的版本环境。例如生成图查询语言时，系统使用的是 Neo4j GDS 2.x 版本，但 AI 仍然生成的是 1.x 版本的语法（如 Map 通配符 {'*': {...}}），导致语法不一致、运行时直接报错。AI 给的是代码片段，人需要保证它在当前环境中能跑。

多会话信息不同步

为保持高效开发往往会开多个会话窗口，一个不注意就会出现会话之间的信息不同步问题。例如通过 yml 中大语言模型输出格式来匹配对应的提示词文档，但当一个会话涉及新功能实现时，就可能修改了匹配的提示词文档后缀，导致与配置文件中的格式不一致，匹配失败。跨文件的契约必须由人来统一和校验。
