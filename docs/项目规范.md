## 第1章 项目概述与范围

### 1.1 项目背景与核心价值

在教育与企业知识管理场景中，AI 执行复杂分析任务时高度依赖上下文质量。当前面临三大挑战：

1. **数据源异构与信息孤岛**：学生成绩、课堂行为、教辅 PDF、视频等分散在不同系统中
2. **上下文关联弱**：传统关键词检索难以揭示"成绩-行为-教师-知识点"间的深层关联
3. **上下文噪音大**：原始数据直接输入 LLM 导致信息截断和"幻觉"

本系统通过 **"多维数据图谱化 → 宽图谱融合 → 任务驱动剪枝 → 动态更新"** 四步技术架构，为 LLM 提供高质量、自适应的上下文支持。

### 1.2 三阶段交付目标

| 阶段 | 目标 | 核心产出 |
|------|------|---------|
| **第一阶段** | 多维数据的深度图谱化构建 | PDF 文档知识图谱 + CSV 成绩事件图谱 → Neo4j |
| **第二阶段** | 基于主数据的宽图谱融合 | 实体对齐 → 以学生/知识点为图钉的宽图谱 → PageRank 度量 |
| **第三阶段** | 端到端问答集成与动态权重 | 图剪枝 → LLM 归因分析 → 权重动态更新（时间衰减+行为调整） |

### 1.4 文档约定

#### 1.4.1 命名规范

以下规范对齐《Java开发手册（黄山版）》执行。

**（一）Java 代码命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 包名 | 全小写，点分隔，单数形式 | `com.graphnexus.infrastructure.neo4j` |
| 类名 | UpperCamelCase | `StudentNode`, `PruningStrategyService` |
| 抽象类 | Abstract 或 Base 开头 | `AbstractGraphNode`, `BaseEntity` |
| 接口名 | 无修饰符，Service/DAO 接口不加 I 前缀 | `GraphNodeService`, `DocumentRepository` |
| 接口实现类 | 接口名 + Impl 后缀 | `GraphNodeServiceImpl`, `DocumentRepositoryImpl` |
| 枚举类 | 带 Enum 后缀 | `NodeLabelEnum`, `TaskTypeEnum` |
| 枚举成员 | 全大写，下划线分隔 | `SUCCESS`, `UNKNOWN_REASON` |
| 方法名 | lowerCamelCase，动词开头 | `findSubGraph()`, `adjustWeight()` |
| Service 层方法 | get(单个) / list(多个) / count(统计) / save|insert(新增) / remove|delete(删除) / update(修改) | `listStudents()`, `saveDocument()`, `updateWeight()` |
| 常量 | 全大写，下划线分隔 | `MAX_STOCK_COUNT`, `CACHE_EXPIRED_TIME` |
| 变量/参数 | lowerCamelCase，类型名词放词尾 | `startTime`, `workQueue`, `nameList` |
| 布尔变量（POJO） | 禁止 is 前缀（用包装类型 Boolean） | `deleted`, `active` |
| 数组 | 类型与中括号紧挨 | `int[] arrayDemo` |

**（二）POJO 类命名后缀**

| 后缀 | 全称 | 用途 |
|------|------|------|
| DO | Data Object | 与数据库表结构一一对应 |
| DTO | Data Transfer Object | Service/Manager 向外传输 |
| BO | Business Object | 封装业务逻辑的输出对象 |
| VO | View Object | 显示层对象，Web 向模板渲染传输 |
| Query | Query Object | 数据查询对象（超过 2 个参数禁止用 Map） |

**（三）数据库命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写蛇形，单数，`业务名_表作用` | `user_account`, `parse_task`, `attribution_query` |
| 字段名 | 小写蛇形 | `student_no`, `created_at` |
| 布尔字段 | `is_xxx`，类型 `unsigned tinyint`（1=是，0=否） | `is_deleted`, `is_active` |
| 必备字段 | 每表必须有 `id`, `create_time`, `update_time` | — |
| 主键名 | `id`，类型 `bigint unsigned`，自增 | — |
| 主键索引 | `pk_字段名` | `pk_id` |
| 唯一索引 | `uk_字段名` | `uk_business_no` |
| 普通索引 | `idx_字段名` | `idx_name` |
| 字符集 | 统一 `utf8mb4` | — |

**（四）REST API 命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| URL 路径 | 小写，资源名词单数，下划线分隔 | `/api/v1/document`, `/api/v1/attribution_query` |
| JSON key | lowerCamelCase | `errorCode`, `menuList`, `assetStatus` |
| 请求方法 | GET(查) / POST(增) / PUT(改) / DELETE(删) | — |

**（五）其他命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 异常类 | Exception 结尾 | `DocumentParseException` |
| 测试类 | 被测试类名 + Test 结尾 | `GraphNodeServiceTest` |
| 错误码 | 5位字符串：来源(A/B/C) + 4位数字 | `A0001`, `B0120`, `C0301` |
| Git 分支 | `feature/story-{id}-{desc}` | `feature/story-1.1-pdf-upload` |
| Git 提交 | `[type] description` | `[feat] 实现PDF上传接口` |

#### 1.4.2 包结构规范

```
com.graphnexus
├── api                          // L1 API 层：Controller + DTO
│   ├── gateway                  //   网关（认证/鉴权过滤器）
│   ├── document                 //   文档处理模块
│   ├── graph                    //   图处理模块
│   ├── analysis                 //   图分析模块
│   ├── query                    //   智能查询模块
│   └── basic                    //   基础数据模块
├── application                  // L2 应用层：Service + Model/BO/Query
│   ├── document                 //   文档处理服务
│   ├── graph                    //   图处理服务
│   ├── analysis                 //   图分析服务
│   ├── query                    //   智能查询服务
│   ├── basic                    //   基础数据服务
│   └── llm-gateway              //   LLM 网关服务
├── infrastructure               // L3 基础设施层
│   ├── neo4j                    //   Neo4j：配置、节点、边、Repository
│   ├── mysql                    //   MySQL：配置、Entity(DO)、Repository
│   ├── redis                    //   Redis：Lettuce 配置、CacheManager
│   ├── mq                       //   消息队列：RabbitMQ Queue/Exchange/Binding
│   ├── storage                  //   文件存储：MinIO Client、Bucket 策略
│   └── llm                      //   LLM API：WebClient 配置、Prompt 模板
└── common                       // 公共模块
    ├── config                   //   公共配置（Jackson、Actuator、CORS）
    ├── exception                //   统一异常体系
    ├── logging                  //   日志（TraceId 过滤器、MDC）
    └── monitoring               //   监控（Micrometer 指标、健康指示器）
```

**分层职责说明**：

| 层 | 目录 | 职责 | 依赖方向 |
|:--|:--|:--|:--|
| **L1 API 层** | `api/` | 接收 HTTP 请求，参数校验，DTO 转换，调用 L2 服务 | 依赖 L2 |
| **L2 应用层** | `application/` | 业务逻辑编排，事务管理，调用 L3 基础设施 | 依赖 L3 |
| **L3 基础设施层** | `infrastructure/` | 数据持久化，外部服务调用，消息通信，缓存 | 不依赖上层 |
| **公共模块** | `common/` | 横切关注点：异常、日志、监控、公共配置 | 被所有层依赖 |

**层间调用规则**：

```
L1 (api) ──调用──▶ L2 (application) ──调用──▶ L3 (infrastructure)
  │                     │                        │
  └─────────────────────┼────────────────────────┘
                        ▼
                  common（被所有层依赖）
```

1. L1 只调用 L2，禁止直接调用 L3
2. L2 调用 L3，禁止反向依赖
3. L1/L2/L3 之间的数据传输使用 DTO（L1↔L2）和 Model/BO（L2内部）
4. common 被所有层依赖，不依赖任何层

#### 1.4.3 代码风格与 OOP 规约

以下规则摘取自《Java开发手册（黄山版）》编程规约·OOP规约·注释规约章节。

| 分类 | 规则 | 说明 |
|------|------|------|
| **依赖注入** | 强制：构造器注入 | 禁止字段 `@Autowired`，使用 `private final` + `@RequiredArgsConstructor` |
| **POJO 默认值** | 强制：所有 POJO 类属性使用包装数据类型 | 数据库查询结果可能为 null，基本类型有 NPE 风险 |
| **覆写方法** | 强制：加 `@Override` 注解 | 避免方法签名不匹配 |
| **equals 比较** | 强制：常量或有值对象调用 equals | `"test".equals(param)` 而非 `param.equals("test")` |
| **包装类比较** | 强制：全部使用 equals 方法 | `Integer` 在 -128~127 外会 new 新对象 |
| **BigDecimal** | 强制：禁止使用 `new BigDecimal(double)` | 存在精度损失，使用 `new BigDecimal("0.1")` 或 `valueOf()` |
| **构造方法** | 强制：禁止加入业务逻辑 | 初始化逻辑放在 `init()` 方法 |
| **toString** | 强制：POJO 类必须写 toString 方法 | 排查问题时直接调用 `toString()` 打印属性值 |
| **访问控制** | 推荐：从严控制 | private > protected > public |
| **类内方法顺序** | 推荐：公有方法 > 私有方法 > getter/setter | getter/setter 放在类体最后 |
| **final 使用** | 推荐：不允许继承/覆写/修改的场景使用 final | Service 注入字段声明为 `private final` |
| **可变参数** | 强制：相同参数类型、相同业务含义才使用 | 可变参数必须放在参数列表最后 |
| **SerialVersionUID** | 强制：新增属性不修改此值 | 完全不兼容升级时再修改 |

#### 1.4.4 注释规约

| 分类 | 规则 |
|------|------|
| **类注释** | 强制使用 Javadoc 格式（`/** 内容 */`），含 `@author` 和 `@date`（格式 yyyy/MM/dd） |
| **方法注释** | Service 层方法强制 Javadoc：描述功能、`@param`、`@return`、`@throws` |
| **枚举注释** | 强制每个枚举字段注释说明用途 |
| **单行注释** | `//` 注释，在被注释语句上方另起一行 |
| **TODO/FIXME** | 须标明标记人、标记时间、预计处理时间 |
| **注释更新** | 推荐：代码修改时同步更新注释 |

#### 1.4.6 分层领域模型规约

对齐黄山版工程结构规范：

```
请求链路中的数据对象转换：
┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
│ 前端/客户端 │ ───▶ │ L1 API   │ ───▶ │ L2 App   │ ───▶ │ L3 Infra │
└──────────┘      └──────────┘      └──────────┘      └──────────┘
       │                │                 │                 │
       ▼                ▼                 ▼                 ▼
   JSON 请求体      DTO/VO            BO/Query            DO/Entity
  (前端约定格式)  (api/**/dto/)  (application/**/model/)  (infrastructure/**/entity/)
```

| 模型类型 | 所在层 | 包路径 | 职责 |
|---------|--------|--------|------|
| **VO**（View Object） | L1 API 层 | `api/**/dto/` | 响应给前端的展示对象，按页面/视图聚合 |
| **DTO**（Data Transfer Object） | L1 API 层 | `api/**/dto/` | Controller 接收的请求体，Service 间传输 |
| **Query**（Query Object） | L2 应用层 | `application/**/model/` | 查询条件封装（超过 2 个参数时使用，禁止用 Map） |
| **BO**（Business Object） | L2 应用层 | `application/**/model/` | Service 层输出的封装业务逻辑的对象 |
| **DO**（Data Object） | L3 基础设施层 | `infrastructure/mysql/entity/` | 与数据库表一一对应 |
| **Command** | L1/L2 | `api/**/dto/` 或 `application/**/model/` | 命令对象（如 MergeCommand、ImportCommand） |

### 2.3 分层调用规范

**调用规则图**：

```
┌────────────────────────────────────────────────────────────┐
│  L1  api/                                                  │
│       Controller + DTO                                      │
│       职责：接收请求、参数校验、VO/DTO 转换、调用 L2          │
│       禁止：包含业务逻辑、直接调用 L3                         │
└────────────┬───────────────────────────────────────────────┘
             │ 调用（通过 Service 接口）
             ▼
┌────────────────────────────────────────────────────────────┐
│  L2  application/                                          │
│       Service + Model/BO/Query                              │
│       职责：业务编排、事务管理、领域逻辑、调用 L3             │
│       禁止：直接操作数据库连接、处理 HTTP 请求/响应           │
└────────────┬───────────────────────────────────────────────┘
             │ 调用（通过 Repository/Mapper/Client）
             ▼
┌────────────────────────────────────────────────────────────┐
│  L3  infrastructure/                                       │
│       Repository + Entity + Config + Client                 │
│       职责：数据持久化、外部服务调用、消息通信、缓存          │
│       禁止：包含业务逻辑                                    │
└────────────────────────────────────────────────────────────┘

       ┌─────────────────────────────┐
       │  common/ （被所有层依赖）     │
       │  config│exception│logging    │
       │  monitoring                  │
       └─────────────────────────────┘
```

**各层数据对象使用规范**：

| 传输场景 | 使用对象 | 说明 |
|---------|---------|------|
| 前端 → L1 Controller | `DTO`（@Valid 校验） | 请求体反序列化，字段含 `@NotBlank` 等 Jakarta 校验注解 |
| L1 Controller → L2 Service | `DTO` 或 `Query` | 参数 ≤ 2 个可直接传递，> 2 个用 Query 对象 |
| L2 Service → L1 Controller | `VO` 或 `BO` | Controller 最终转 VO 返回前端 |
| L2 Service → L3 Repository | `DO`（或 Neo4j Node/Edge） | 与数据库存储一一对应 |
| L1/L2 内部 | `DTO` / `BO` | 跨层不直接传 DO，避免持久化细节泄露 |

**事务管理规范**：

| 规则 | 说明 |
|------|------|
| 事务注解位置 | `@Transactional` 仅放在 L2 Service 方法上，不放 L1 Controller |
| 只读优化 | 查询方法加 `@Transactional(readOnly = true)` |
| 回滚策略 | 默认 RuntimeException 回滚，checked 异常使用 `@Transactional(rollbackFor = Exception.class)` |
| 事务边界 | 单 Service 方法为一个事务，避免跨 Service 的大事务 |
| 分布式事务 | 图数据库（Neo4j）与关系数据库（MySQL）的事务独立，通过消息队列最终一致 |

**异常传递规范**：

| 层级 | 异常处理方式 |
|------|-------------|
| L3 基础设施 | 捕获技术异常（SQLException、CypherException），向上抛出自定义 `BusinessException`，**不在此层记日志** |
| L2 应用层 | 捕获并记录日志（含参数和上下文），可重新抛出或转换为业务异常 |
| L1 API 层 | **禁止向上抛异常**。由 `GlobalExceptionHandler` 统一处理，返回 ErrorResponse |

// TraceIdFilter 核心逻辑
protected void doFilterInternal(HttpServletRequest request, ...) {
    String traceId = Optional.ofNullable(request.getHeader("X-Trace-Id"))
                              .orElse(UUID.randomUUID().toString());
    MDC.put("traceId", traceId);
    try { filterChain.doFilter(request, response); }
    finally { MDC.remove("traceId"); }
}

## 第3章 数据库设计规范

对齐黄山版 MySQL 规约，以下条款 **强制** 执行：

| # | 条款 | 本方案落实 |
|:--|------|-----------|
| 1 | 表名、字段名必须小写字母或数字，禁止数字开头 | 全部采用小写蛇形命名 |
| 2 | 表名不使用复数名词 | `user_account`、`parse_task`、`attribution_query` 均为单数 |
| 3 | 禁用保留字（如 desc、range、match 等） | 字段名已核验，无保留字冲突 |
| 4 | 主键索引 `pk_字段名`，唯一索引 `uk_字段名`，普通索引 `idx_字段名` | 所有索引按此规范命名 |
| 5 | 小数类型为 **decimal**，禁止使用 float 和 double | 权重、置信度、得分等小数字段全部使用 decimal(m,n) |
| 6 | varchar 长度不超过 5000，超长用 text 独立建表 | varchar 字段统一控制在 50-500 范围 |
| 7 | 表必备三字段：`id`（bigint unsigned 自增）、`create_time`（datetime）、`update_time`（datetime） | 所有表均包含此三字段 |
| 8 | 布尔字段：`is_xxx`，类型 `unsigned tinyint`（1=是，0=否） | `is_deleted`、`is_active`、`is_preset` 等 |
| 9 | **全部使用逻辑删除**，禁止物理删除（日志类表除外） | 业务表均含 `is_deleted` 字段；纯日志表（`login_log`/`audit_log`/`llm_call_log`）不设逻辑删除 |
| 10 | 不得使用外键与级联，外键概念在应用层解决 | 表间关联通过应用层代码维护，禁止 `FOREIGN KEY` 约束 |
| 11 | 禁止使用存储过程 | 全部业务逻辑在 Java 应用层实现 |
| 12 | 字符集：`utf8mb4`，存储引擎：InnoDB | 建表语句统一指定 |
| 13 | 字段注释：`COMMENT` 必写 | 每个字段均含 COMMENT |

**字段冗余策略**（黄山版推荐）：

> 以下场景允许适当冗余：① 非频繁修改的字段 ② 非唯一索引字段 ③ 非 varchar 超长字段。如 `parse_result` 表中的 `entity_count`/`relation_count` 即为冗余字段，避免每次列表查询需 JOIN 统计。

**分库分表策略**（黄山版推荐）：

> 预计三年内单表数据量不超过 500 万行或容量不超过 2GB 的，不提前分库分表。当前 MVP 阶段全部表单表存储，后续按需拆分。

**varchar 索引前缀**（黄山版·索引规约）：

> varchar 字段建索引时，按 `count(distinct left(列名, 索引长度)) / count(*)` 计算区分度，取区分度 > 90% 的最小长度作为前缀索引。
